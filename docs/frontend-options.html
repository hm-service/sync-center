sync-center 前端方案对比

面板要展示的内容很固定：命名空间、快照、文件树、预览。差别只在用什么方式组织这几块，以及文案怎么保证不漏。

现状

A. 原生 JS

一个 index.html 加几个 js 文件，手写词典和 DOM 渲染。

  • 零依赖，产物就是几个静态文件
  • i18n 靠约定，漏配只能在界面上发现
  • 文案一多，DOM 拼装会很啰嗦
推荐

B. Vue + Vite + TS

组件化，词典带类型，构建产物仍然是一组静态文件，照旧 go:embed。

  • 词典类型化，漏 key 或漏语言在 typecheck 阶段就报错
  • 语言切换、响应式渲染都是框架内置能力
  • 代价是多一套 node 构建链
备选

C. Go 模板

用 html/template 在服务端渲染，前端不写 JS。

  • 没有构建步骤，二进制度更小
  • 交互（树展开、预览切换）要靠整页刷新或少量 JS
  • i18n 和后端共用一套词典，但前端仍要写内联脚本

逐项对比

维度A. 原生 JSB. Vue + Vite + TSC. Go 模板
漏配文案能否在构建期发现不能能，typecheck 报错不能
语言切换手写重渲染响应式，改一个 ref整页刷新
文件树 / 预览交互手写 DOM组件 + 模板需要额外 JS
构建产物3 个静态文件带 hash 的静态文件无
新增依赖无vue / vite / typescript无
维护成本随文案增长上升稳定交互一复杂就上升

为什么选 B

这个面板的用户可见文案已经接近 40 条、两种语言，靠“漏了会显示键名”来兜底只在开发时有效，上线后就是用户看到 ui.title。把词典放进 TypeScript，让 t() 的参数类型是 keyof typeof messages，漏配直接编译不过，这是 A 和 C 都给不了的。

构建产物仍然落到 frontend/dist，被 go:embed 编进二进制，部署形态不变。

词典的形状

const messages = {
  "ui.title": { zh: "sync-center", en: "sync-center" },
  "ui.updated-at": { zh: "更新于 {time}", en: "updated {time}" },
} as const;

type Key = keyof typeof messages;

function t(key: Key, params?: Record<string, string | number>): string {
  // 缺失 key 是类型错误，缺某一列也是类型错误
}

迁移代价

后端只改一处：/auth、/admin、/ 都返回同一份 index.html，由前端根据路径决定渲染登录页还是面板。API 契约、路由、鉴权都不动。
